# 主机级端口转发常驻:独立转发连接,解耦会话

`host.Forwards` 从「会话建立时编程到会话连接、随会话销毁关闭」改为「运行在主机专属的转发连接上,不随任何会话生灭」。会话级转发(会话内临时添加)维持原语义。

## 背景

转发 Registry 原以 session 为键(`ForwardRegistry.bySession`),主机级转发在每次会话建立时经 `applyHostForwards` 绑定到该会话的 SSH 连接,会话销毁即关闭——转发依赖会话。用户诉求:「端口转发保持常驻,不依赖连接」;SSH 转发的物理本质是连接上的 channel,不能脱离连接,但可以脱离**交互会话**:转发拥有自己的连接并自行管理生命周期。

## 决策

- **per-host 转发连接**(Step A):每台主机至多一条「转发连接」,由 `ForwardHostManager`(key=hostID)持有,复用与 session 拨号完全相同的链路(`sshx.BuildHop` + TOFU + `sshx.Dial` + keyring 凭据解析),但不开 PTY——连接只承载转发。
- **触发**:会话建立时 `ensure(hostID, prov)`(幂等):连接未起则拨号并拉起 `host.Forwards`;已起则补 reconcile。主机记录变更(`PUT /api/hosts`)→ `reconcile` diff 启动/撤销;主机删除 → `release`;服务退出 → `closeAll`。
- **凭据策略(A-1「借凭据再拨一条」)**:key/钥匙串凭据可无头拨号;仅存在于浏览器的密码,由该主机任一会话建立时的请求顺带作为转发连接的拨号凭据——服务端以相同凭据另拨一条转发连接,**不移交会话连接**。浏览器密码用户因此也能常驻,零额外输入。
- **运行时视图**:`GET /api/hosts/{id}/forwards` 返回每条转发的状态(running/pending/failed + 错误信息);会话级转发端点(`/api/sessions/{id}/forwards`)不动。
- **同主机多页签共享同一组转发**,不再端口冲突(旧模型每会话绑一次,二次绑定失败)。

## 理由

- 主机级转发的配置本就写在主机记录上(`hosts.json`),归属天然是主机而非会话;旧实现的「绑定会话」只是实现捷径,不是领域语义。
- 独立连接使「关终端页签/毁会话不丢转发」成为结构保证,而非保活技巧(旧模型的替代方案——会话关时保活连接——会把 PTY 生命周期拖进转发生命周期,污染 gotty 移植的会话状态机)。
- 拨号与凭据解析全量复用现有 `sshx` 管线,无新传输层;forward launch 逻辑抽出为 `launchOnClient`,会话级/主机级共用,行为一致。

## 代价

- 转发连接在服务期间常驻:每次服务的转发连接一般只此一条/主机;断线后不自动重连(状态标 failed,下次会话或配置变更重拨)——自动重连、服务重启自动恢复、UI 开关属 **Step B**,本步刻意不做(见边界)。
- 密码仅存浏览器的场景,转发连接必须等该主机出现过一次会话才能建立(首会话之前转发处于 pending)。
- 失败语义:单条转发失败不阻断其余(延续旧「单个失败不阻断连接」);转发连接拨号失败不影响任何会话(独立连接)。

## 备选

- **A-2 主机共享连接**(同主机终端与转发共用一条连接):一次鉴权全复用,但需重构 gotty 移植的会话生命周期(抢占/空闲超时/状态机围绕共享连接),改动大,留待评估。
- **会话保活**(关页签时保留会话连接):连接会随会话瞬时状态变动,PTY 与转发生命周期耦合,语义脆弱,否决。
- **常驻服务化(Step B)**:转发连接独立拨号 + 指数退避重连 + 服务启动自动恢复 + UI 开关;是 A 的延伸,复用本步的管理器与状态视图,另行立项。
